## 3. 근본 원인 (Root Cause)
**GCP 호스트 인프라 장애.** 판단 근거:
1. **단일 시점 77분 백로그 폐기** = 게스트 클럭이 점프 = 하이퍼바이저 VM stun/freeze (스레드 starvation이면 점진적이어야 함).
2. **링크로컬 메타데이터 서버(169.254.169.254) unreachable** = 외부 인터넷이 아니라 VM↔호스트 가상 네트워크 경로 장애.
3. **ACPI "Power key pressed"** = 외부(GCP) 발신 전원 신호. 게스트 내부 `reboot`/`shutdown` 명령 흔적 없음.
4. 인스턴스 정책은 정상(`onHostMaintenance=MIGRATE`, `automaticRestart=TRUE`, 비-preemptible). 정상이면 무중단 라이브 마이그레이션돼야 하나, 호스트가 비정상이라 마이그레이션이 실패/지연되고 결국 강제 종료+건강한 호스트로 재기동된 것으로 추정.
5. 커널 업그레이드(1054→1060)는 **결과**일 뿐 원인 아님 — 장애(15:33) 이후 강제 재부팅이 사전 스테이징된 커널을 집어든 것. `Automatic-Reboot "false"`라 apt가 재부팅을 유발하지 않았음.

→ **우리 코드/설정 결함이 아니라 클라우드 인프라 단일 이벤트.** 직접 예방은 불가, 단 **탐지·복원력·통보**를 강화할 수 있음.

## 6. 재발 방지책 (우선순위)
### P0 — Off-VM 통보 (오늘 가장 아팠던 공백)
- VM 네트워크가 죽으면 봇이 알림을 못 보냄. **VM 외부에서 도는 dead-man's-switch** 도입:
  - healthchecks.io(무료) 또는 GCP Cloud Monitoring **uptime check + alert policy**.
  - 봇이 장중 5분마다 ping → N분 무신호 시 **이메일/푸시(SMS)** 외부 발신.
  - GCP 알림 정책에 **인스턴스 reset/uptime 리셋** 트리거 추가(호스트 이벤트를 클라우드 콘솔이 직접 감지).

### P0 — 누락 핵심 잡 탐지 + 복귀 시 강한 알림
- 현재는 잡이 조용히 폐기됨. 서비스 기동/네트워크 복구 시 **"오늘 실행됐어야 할 핵심 잡(스크리닝/자동매수/보유기간매도/모니터링) vs 실제 실행"을 대조해 누락분을 텔레그램+외부로 경보**.
- **장중(09:00~15:30)에 서비스가 새로 start되면 = 비정상 재시작**이므로 즉시 경보 + 포지션 재점검 트리거.

### P1 — 기동 시 포지션 재조정 + 모니터링 즉시 재무장
- 서비스 start 시 KIS 잔고와 portfolio(holding) 대조, **monitoring 즉시 재가동**, 장중 기동이면 트레일링 상태 복원 검증.

### P2 — 코드/인프라 잔손질
- KIS/네트워크 호출에 **명시적 짧은 타임아웃** — 행(hang) 자원 점유로 스케줄러 스레드풀 고갈 방지(이번엔 stun이 주원인이나 방어 가치 있음).
- telegram listener DNS 실패 시 **지수 백오프**(현재 5초 간격 스팸).
- 커널 업데이트는 **주말 통제된 시간에 의도적 재부팅**으로 적용(예고 없는 GCP 재부팅에 스테이징 커널이 묻어가는 것 방지).
- `onHostMaintenance=MIGRATE`/`automaticRestart=TRUE`는 이미 최적 — 변경 불필요. 동일 호스트 장애 재발 시 GCP 지원 케이스 + 머신 재배치 고려.
